# ADR-002: Neon PostgreSQL for Persistent Audit Chain Storage

**Date:** 2026-06-17  
**Status:** Accepted  
**Deciders:** Portfolio author

## Context

The initial release stored all audit events in client-side React state (seeded from `lib/demo-data.ts`). The hash chain was computed and verified in the browser on every render. This was correct for a zero-dependency portfolio demo but left the tamper-evident audit trail with no persistence across page reloads, and offered no server-side verification endpoint that an auditor or integration partner could call independently of the UI.

The Neon serverless PostgreSQL instance (already provisioned) closes this gap with minimal added complexity.

## Decision

Persist reviewer-triggered audit events to a Neon PostgreSQL table (`audit_events`) via a Next.js App Router API route. Expose a public `GET /api/audit/verify` endpoint that re-derives and verifies the full chain from the database independently of the frontend.

## Schema

```sql
CREATE TABLE audit_events (
  id             TEXT PRIMARY KEY,
  sequence_number INTEGER NOT NULL,
  timestamp      TEXT NOT NULL,
  actor          TEXT NOT NULL,
  action         TEXT NOT NULL,
  target_type    TEXT NOT NULL,
  target_id      TEXT NOT NULL,
  before_status  TEXT NOT NULL,
  after_status   TEXT NOT NULL,
  note           TEXT NOT NULL,
  chain_hash     TEXT NOT NULL,   -- SHA-256(payload | previous_hash)
  previous_hash  TEXT NOT NULL,   -- pointer to prior event's chain_hash
  created_at     TIMESTAMPTZ DEFAULT NOW()
);
```

`chain_hash` and `previous_hash` are stored alongside each row so the verify endpoint can re-run the chain-walking algorithm without recomputing all hashes from scratch — it only needs to confirm that each stored hash is consistent with its stored inputs.

## API surface

| Route | Method | Purpose |
|-------|--------|---------|
| `/api/audit` | POST | Persist a new reviewer audit event; server appends to chain |
| `/api/audit/verify` | GET | Re-verify full chain from DB; returns `{ valid, totalEvents, firstBrokenAt }` |

The server-side chain append (`lib/audit-chain.ts → appendEvent`) uses the same SHA-256 algorithm as the client-side `buildChain`, ensuring the DB-persisted chain is verifiable by either side.

## Why Neon + Drizzle ORM (not raw SQL, not Prisma)

- **Neon serverless (`@neondatabase/serverless`)** provides an HTTP-based driver (`neon()`) that works in Next.js App Router routes without WebSocket configuration or connection pool tuning.
- **Drizzle ORM** adds type-safe query building with zero query-builder overhead and a schema-first migration path (`drizzle-kit push`) — appropriate for a single-table addition that doesn't warrant Prisma's full codegen cycle.
- The schema fits in one file (`lib/db/schema.ts`) and the connection in another (`lib/db/index.ts`), keeping the footprint small.

## What is not persisted

Seed data (`lib/demo-data.ts`) and the in-memory compliance state (evidence item status changes, gaps, package evaluation) remain client-side. Only audit events generated by live reviewer actions in the UI are written to the database. This is intentional: seed data is synthetic and deterministic; the demo resets to the same state on reload.

## Consequences

- `npm run dev` now requires `DATABASE_URL` in `.env` to serve API routes without errors. The frontend-only views (Dashboard, Controls, Gaps, Package) work without a DB connection.
- CI does not run `db:push` or attempt DB connectivity; the test suite (`npm test`) covers `appendEvent` unit tests without a database dependency.
- The verify endpoint at `GET /api/audit/verify` is stateless and cacheable — it returns a chain integrity report that could be polled by a monitoring system or included in a SOC 2 evidence package.
